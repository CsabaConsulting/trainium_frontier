## Seed discipline (no seed hunt — dropped 2026-09-16)

A public-best seed hunt is selection bias: best-of-N on the visible eval
overstates the true gain, and expected transfer to the pinned private shard is
~zero. Worse, locking a "lucky" seed early distorts every later comparison.
Instead: **fix seed 42 as the control seed for all comparisons**, and only at
the very end re-verify the final config on 2–3 seeds, judging by the average
across eval defs, never the public-best outlier. Use the known spread (~0.006)
as a significance bar: future improvements must clear ~0.003 to count as
signal, not noise.

4. **FP8 — STAGED RESEARCH TRACK (reopened 2026-09-16, user call).**
   What died: the TORCH-LEVEL emulation path (Fp8Linear wrapper + `_scaled_mm`):
   numerically exact (loss OFF=ON=10.824890) but 14.9x slower per micro-step —
   that verdict stands for that path (`run-logs/fp8_probe3/4`, `fp8_mlp_hw`,
   `fp8_full_model`). What was NEVER tried: the NATIVE compiler path. Trainium2
   silicon delivers 1,299 FP8 vs 667 BF16 TFLOPS (official arch docs), and
   `neuronx-cc compile` accepts `--auto-cast <mode> --auto-cast-type fp8_e4m3`
   (verified on-box 2026-09-16 in native_venv's own compiler 2.26 — top-level
   `--help` hides it, `compile --help` shows it; no upgrade needed).
   WHY THE OLD PROBES DON'T COUNT. (a) The NaN: `torch.matmul(fp8,fp8)` on the
   eager stack hits an unimplemented ATen kernel → garbage out. Values were
   innocent (absmax 6.5; identical values correct through `_scaled_mm`). (b) The
   14.9x: the probe's own `Fp8LinearFn.forward` upcasts to float BEFORE the
   matmul (`torch.matmul(x_fp8.float(), ...)`), so no FP8 GEMM ever executed —
   the slowdown measured the emulation scaffolding, not FP8. (c) Venv lineage:
   everything runs in custom `native_venv` (torch-neuronx EAGER editable install
   2.11.3+unknown.dev, neuronx-cc 2.26). Supplied DLAMI venvs (`/opt/
   aws_neuronx_venv_*`, 2.27-based) and `xla_venv` (torch-xla 2.11, nki 0.6.0)
   exist but have never run our train.py; xla_venv's compiler help shows NO
   auto-cast flags. Flag delivery works via `NEURON_CC_FLAGS` env (proven by
   the --optlevel=1-vs-2 control in train.py comments).
   - Stage 1 (done 2026-09-16): flag verified present; no upgrade needed.
     Scaled expectation: our graph is already bf16 (COMPUTE_DTYPE) and
     auto-cast converts FP32 ops — the win is bounded by remaining fp32 matmul
     mass, likely moderate, not 2x. Sources below.
   - Stage 2 (300-step smoke 2026-09-16): COMPILE OK, **+34% throughput
     (0.63 s/step, ~208k tok/s vs 0.84/155k) — but loss FROZEN at init 9.0113
     for all 300 steps: no learning at all.** Log: sub1-p2b-autocast-smoke.
     Throughput win is real; convergence failure is total (not slow — absent).
     Running control: matmult/bf16 smoke (same flag, bf16 type) to isolate
     fp8-specific vs structural breakage. If bf16 learns: fp8 kills grads
     (scale/underflow?) → try narrower scope or loss scaling. If bf16 also
     frozen: the flag breaks the graph structurally (NKI interplay?) → dump
     NEFF cast placement, then kill.
     CAST-BOUNDARY DISCIPLINE (user call 2026-09-16): every upcast the compiler
     inserts (fp8 GEMM → fp32 accumulate → bf16 store → next op) is a memory
     pass that eats the matmul win unless the pipeline stays fp8 across it.
     Therefore: prefer the matmul-only cast mode over `all` (keep RMSNorm,
     softmax, and the Muon/AdamW optimizer math in bf16/fp32 — less cast
     churn AND less convergence risk); note our fused NKI kernels
     (softcap+CE, rope+norm, Muon) are opaque to auto-cast, so only the
     aten/XLA part of the graph can benefit — the win is bounded twice over.
     Watch (a) compile success — known risk: activation-table-limit errors on
     transformer backward (upstream issue #1314); (b) NET steps/s vs 0.84
     baseline (the only number that matters — never infer from op counts);
     (c) loss sanity (keep grad-clip on, be ready with loss scaling). On a
     neutral/negative smoke, dump compiler cast placement (verbose NEFF log)
     to see whether cast boundaries ate the win before killing: a boundary
     problem is fixable (narrower cast scope), a no-win is terminal.
     Kill: compile fails unfixably, or net steps/s ≤ baseline with no
     boundary explanation, or loss diverges.
   - Stage 3 (full 1800 s, seed 42): only on a stage-2 win. Score raw bpb.
   Sources: awsdocs-neuron trainium2 arch (TFLOPS), neuronx-cc 2.27 release
   notes (flag), Medium/TDS Neuron optimization tutorial (pattern + stability
   caveats). Fits the ~2-week horizon; queued after wave-2 runs.
   INT8 / SPARSE (user call 2026-09-16): checked, NOT queued. Zero prior
   experiments in history (no labels/logs); `neuronx-cc compile --help` on our
   2.26 exposes no int8/sparsity/pruning flags (only an MX scale-computation
   mention) — the arch's "sparse TFLOPS" live in NxD inference kernels, not in
   any training path we can flip. Manual int8 emulation would repeat the dead
   Fp8Linear trap by construction. Reopen only if a native training entry
   point appears (new SDK flag or NKI sparse-GEMM example).
