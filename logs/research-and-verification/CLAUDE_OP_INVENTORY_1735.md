## How the estimates were made

Calibration supplied by the team (all per micro-step unless stated):

| symbol | meaning | value |
|---|---|---|
| P1 | one compiled elementwise pass over a [BT, C] bf16 tensor (read 64 MiB + write 64 MiB) | 1 to 2 ms (1.5 used) |
| PH | one compiled elementwise pass in per-head layout [B, T, H, D] (256 B rows per partition) | about 6 ms |
| N | one compiled RMSNorm at [BT, C], fwd + bwd, as measured by removing 18 sites | about 1.1 ms |
| G | one compiled scalar-gated add `x + g*e` at [BT, C], fwd + bwd | about 5.4 ms (about 2 fwd, 3.4 bwd; the bwd includes the 0-dim gate reduction `sum(grad*e)`) |

| big | passes over [BT, F] (256 MiB) tensors | byte-scaled P1 = 6 ms as the high bound; 2 ms as the low bound (40 % of DMA peak, which is what the fused norm achieves) |
| idx | `index_put` of 32,768 rows into a large sink | 5.64 ms measured (128-wide fp32 rows); per-index-tile latency model, so wider rows cost little extra |
| gather | `table[ids]` gather of 32,768 rows | 0.56 ms measured for 128-wide bf16 rows |

Two facts that shape the whole table:

1. The forward/backward joint graph was traced with AOTAutograd on CPU at tiny shapes (B = 2, T = 128) to count aten nodes exactly (script: scratchpad `trace_graph.py`; NKI kernels fall back to their eager compositions there, everything else is the same graph the Neuron backend receives). With the `default_partition` partitioner the forward holds 40 separate `rms_norm` decompositions (30 `norm()` sites + 10 RoPE fallbacks); with `min_cut_rematerialization_partition` the FX CSE pass collapses the four norms of the same tensor per attention block, leaving 25. The Neuron backend's partitioner choice is not visible from this file, so the duplicated norms are counted as real and the "norm once" rewrite (Z1 below) is listed as zero-risk either way. The backward graph holds 42 gradient-accumulation `add` nodes on [BT, C] bf16 tensors, 2 full-size `slice_backward` zero-fills on [BT, C] (the 32-channel gate inputs), 2 `embedding_dense_backward` scatters, and one `add` on the [BT, V] bf16 logits gradient (the two MTP cross-entropy gradients are summed).
2. The sum of the isolated estimates (high column) is roughly 2.5x the residual budget (446 ms micro-step minus 146 ms matmul minus about 137 ms attention layout minus about 35 ms of kernel runtime = about 128 ms), so the compiler is fusing many of these ops into their neighbours. The "low" figures assume that fusion and DMA-efficient lowering; they sum to about 190 ms, close to the budget. Ranking is by the midpoint. Removing one op from a fused chain saves less than its isolated estimate unless the whole chain goes, which is the argument for kernel-level fusion rather than op-by-op surgery.

Important discrepancy with the brief: in this file the MLP forward is NOT an NKI kernel. `_fused_mlp_kernel` (line 766) calls `reference_forward` (lines 762-764), pure PyTorch, and `kernels/` is empty. If the fused ReLU^2 forward kernel exists in another draft, rows 2a to 2c below vanish there but the backward rows (2d to 2g) remain.

## Region-by-region notes (what each line does and why it costs)

**Embedding site (1013-1029).** `wte(idx)` gathers fp32 rows (128 MiB written), `.to(COMPUTE_DTYPE)` writes them again as bf16; `rows[..., :128]` (1022) is a strided view of the eager-gathered [BT,256] rows and its consumer `value_bigram_proj` (a [BT,128]x[128,1024] matmul, K = 128) probably copies it contiguous (8 MiB); `rows[..., 128:256].repeat(1,1,8)` (1025) writes 64 MiB and its backward is a sum over the 8 copies; `x + gate*projected` (1027) is the measured 5.4 ms gated add; `norm(x)` (1028) then `x0 = x` (1029): x0 feeds all eight blocks, so its gradient is accumulated seven times in the backward (row 4).

**Block (825-844).** Line 826 is the mix (row 5). For attention blocks: line 829 binds q_in = k_in = v_in = x BEFORE the conv add, line 831 norms that same x for the conv, so lines 831 and 834 (or 836-838, the D2 path for block 7) compute the SAME norm four times (row 6). Line 831's add, 840's add and 843's add are residual adds (row 12); each split of x into (norm consumer, residual consumer) costs one accumulation add in the backward (row 4). Line 842 is dead for the pinned injection.

**Attention (728-760).** 730-731 `.view` free; 734 bigram gated add in [BT,C] layout (row 3c); 735 `.view` free; 736-738 GQA repeat is dead (n_kv_heads == n_head); 739-742 the ve gate in per-head layout (row 3a); 743 no-op cast; 744-745 kernels; 746-748 transposes (row 1); 749 SDPA (the compiled attention itself; its internal softmax/mask traffic is inside the team's 25 to 30 ms per layer figure); 750 explicit transpose copy (row 1); 751-752 dead; 753 matmul. `bigram_delta` (755-760): slice (row 16), tiny matmul, sigmoid, no-op cast, `repeat_interleave` (row 3c).

**MLP (762-813).** Row 2. `x.reshape(tokens, C)` (812) and `result.reshape` (813) are free. The backward (785-793) recomputes `relu.square()` on the transposed copy, forms `relu*2.0` as a separate tensor, multiplies, and transposes `dx` back; `dup`/`ddown` casts are no-ops because `up`/`down` are the cached bf16 weights.

**Loss / MTP (616-665, 1041-1049).** Row 10. Everything on [32,1024] (targets shift, mask, weights) is tiny. The second CE kernel pair is the duplicated work; the [BT,V] gradient sum is the hidden add. With `mtp_weights[1] == 0` late in training the second call still runs (by design, line 650: "Do not branch on weights").

**Detached table (984-1010, 1101-1209).** Row 13. `bigram_hash` and the gather run eagerly every micro-step before the compiled call; `table_context` is a Python dict (no device cost); `accumulate` issues one H2D (`weight`, line 1173) that syncs right after the backward; `_update` runs two eager 128 MiB `copy_` calls that a buffer rebind would avoid.

**Per-step glue (1636-1727).** Row 14 plus row 7. Note `refresh_weight_cache` runs at step 0 (1646-1648) and after every optimizer step (1688-1689), 40 eager casts each time.

**Eval path (1508-1524) versus training (item 13).** No divergence found. `load_for_eval` builds the same `GPT`, loads strict weights, and runs `forward_core` EAGERLY (`_d1_compiled_core` is None, line 1007-1009), with the same kernels when the shape guards hold (T % 128 == 0, contiguous inputs) and the same eager fallbacks otherwise, so the math is identical to training up to compiler fusion effects. Differences that are eval-only costs, not semantics: `Linear._cached_weight` is never refreshed in eval so line 681 casts every weight on every call; `mtp_weights is None` triggers a `torch.tensor` H2D at 1047 only when targets are given; the `NEURON_CC_FLAGS` auto-cast flag at line 37 is only set under `__main__`, which does not matter for an eager eval. `EVAL_MIN_SEQ_LEN = 8192` resizes the rotary buffers; `cos[:, :t]` (1015) keeps the kernel guard `cos.shape[1] == t` true.

**Graph-break audit (item 14).** Inside `forward_core` there are no prints, no `.item()`, no data-dependent shapes, and the Python conditionals are on config booleans and static shapes (dynamo specialises them). `_FusedMLP` and `_Conv2NKI` are traceable (pure aten / `wrap_nki` custom op). Two things to verify on the device, in this order:
1. `_RopeNormNKI` (297-316) calls the bare `@nki.jit` functions `_rope_norm_fwd` / `_rope_norm_bwd` directly, whereas the CE and conv kernels are wrapped with `torch_neuronx.wrap_nki` (446-448, 589-590) and launched with a `[lanes]` grid. If dynamo cannot trace the bare `nki.jit` call inside an `autograd.Function.forward`, the whole `apply` becomes a graph break: 10 breaks per micro-step, splitting `forward_core` into 11 compiled subgraphs with eager hand-offs (and 11 backward graphs). Check with `TORCH_LOGS=graph_breaks` (30 minutes). If it breaks, wrapping the two kernels exactly like the other two is a zero-engineering fix. Independently, the bare call without a `[2]` grid may run the kernel on one physical core of the LNC2 pair (the SDK release notes say LNC2 kernels rely on an SPMD launch grid matching the LNC degree); if so, sharding the `BT // P` tile loop over `nl.program_id(0)` and launching `[2]` halves the RoPE kernel time (about 10 calls x 0.5 to 1 ms).
2. `mtp_cross_entropy` and `softcap_cross_entropy` call `selected_lanes(z.shape[0])` and `logits.is_contiguous()`: static under `dynamic=False`, fine. `torch.compile(..., dynamic=False)` without `fullgraph=True` means any break is silent; add `fullgraph=True` once to assert there are none.

## Biggest surprises

1. **The backward graph carries 42 gradient-accumulation adds on [BT, C] bf16 tensors** (row 4), none of them visible in the source. Fifteen come from norming the same tensor three extra times per attention block, seven from `x0` feeding all eight blocks, four from the U-Net skip sources, and the rest from the residual/norm splits and the two gate slices. Together with the 30 norm sites this is why "small" [BT, C] glue adds up to tens of milliseconds.
2. **The MTP second target costs a full second softmax pass and a 1.5 GiB gradient add** (row 10): the two `_SoftcapCrossEntropyNKI` calls each stream the 512 MiB logits in forward and write a 512 MiB gradient in backward, and autograd sums the two gradients with a compiled elementwise add over [32768, 8192] bf16. The logsumexp is the same for both targets, so half of the CE work is recomputation. Estimated 12 to 35 ms per micro-step, and it does not shrink when `mtp_weights[1]` reaches zero.
3. **The MLP forward in this file is plain PyTorch** (rows 2a-2c): `relu`, `square` and `relu.T.contiguous()` are three passes over 256 MiB tensors per block, and the backward adds `relu.square()` recompute, `relu*2.0`, the product, and a `dx` transpose. Byte-scaled calibration says 320+ ms, which is impossible against the 446 ms total, so the compiler is fusing much of it, but whatever survives is on the largest tensors in the model. This needs the profile before the E3(iii) kernel is scoped.
4. **The layer-7 value site is three sites in one** (row 3): a per-head ve gate (two per-head passes forward, two backward), the bigram gate with a materialised `repeat_interleave` and a segmented 128-group reduction in backward, and the `rows[...,128:256].repeat(1,1,8)` at line 1025 with its own 8-way reduction backward. 35 to 50 ms for one layer's value path.
5. **The differentiable weight cache moves 40 gradient casts per micro-step and the cross-micro-step gradient accumulation into eager mode** (row 11): 184 MiB of bf16 grads become 369 MiB fp32 through 40 eager `ToCopyBackward` nodes, and on the second micro-step 40 eager fp32 `AccumulateGrad` adds move 1.1 GiB.
6. **Scalar gates are expensive in backward, not forward**: each of the 21 scalar gates (16 mix lambdas, 4 skip gates, 1 embedding gate) needs a full reduction `sum(grad * operand)` over 33.5 M elements. The measured 5.4 ms gated add is mostly that reduction. E5b/E3 kernels should emit per-partition partial sums and let torch reduce [128, 1].
7. **The embedding tables cost two scatters and four cast passes per micro-step** (row 9): fp32 gathers written twice (fp32 then bf16), bf16-to-fp32 grad casts, and two `embedding_dense_backward` scatters in the same latency-bound class as the table's 5.64 ms `index_put`.
8. **Two 32-channel gate inputs cost two full 64 MiB zero-fills in backward** (row 16): `slice_backward` materialises a [BT, C] zero tensor to scatter a [BT, 32] gradient into, twice, and each then accumulates into the v_norm gradient.
9. **The RoPE kernel is the only one not wrapped with `wrap_nki` and not launched with a lane grid** (graph-break audit). If it graph-breaks, every other estimate in this table is affected because the core is then 11 graphs, not one.

## Zero-engineering fixes (pure PyTorch, identical math unless noted)

- **Z1. Norm once per attention block (lines 829-838).** Replace `norm(x)` at 831 and the three norms at 834/836-838 with a single `xn = norm(x)` computed once before the conv add and passed as `q_in`, `k_in`, `v_in` and the conv input: `xn = norm(x); x = x + self.local_conv(xn); attn_out = self.attn(xn, xn, xn, ...)`. Removes 15 norm fwd+bwd (about 16 ms at the measured 1.1 ms each) and 15 accumulation adds (row 4, 7 to 30 ms) per micro-step if the backend does not already CSE them (it does not with `default_partition`; it does with `min_cut_rematerialization_partition`). Values are bit-identical in forward; the backward sum into grad(x) changes its bf16 accumulation order (the comment at line 833 is about that order), so verify loss curves match to noise.
- **Z2. Two-target CE through one autograd.Function (line 645-660).** Even before the kernel exists, one `autograd.Function` that calls the existing fwd kernel once for target 1 and derives `second = lse - 15*tanh(z.gather(-1, t2)/15)` from the returned `lse` removes the second forward kernel pass (3 to 5 ms). The backward still needs a combined-gradient kernel to avoid the 1.5 GiB add, so this is a half-step; the kernel (K1 below) is the real fix. Requires exposing `lse` from `_softcap_ce_fwd_native` (it is already computed and saved).
- **Z3. One gate projection instead of two (lines 725-726, 741, 756).** Concatenate `ve_gate` [8,32] and `bigram_gate` [8,32] into one `Linear(64, 16)` applied to `x_v[..., :64]` (block-diagonal weight: rows 0-7 read channels 0-31, rows 8-15 read channels 32-63). Identical math only if the off-block weights are held at zero (mask them after each optimizer step, or keep two Linears but feed both from one contiguous `x_v[..., :64]` slice, which already halves the slice_backward zero-fills and the accumulation adds: 2 to 4 ms).
- **Z4. Drop `.to(torch.bfloat16)` from `norm` (line 176).** It is a no-op at every call site today; removing it makes the norm decomposition one node shorter and removes a trap if any input ever becomes fp32 (the extra cast would then silently hide a dtype bug).
- **Z5. Skip the logits slice when `padded_vocab_size == vocab_size` (line 1042).** Free on torch 2.14 (`alias`), but on an older SDK torch it could be a 512 MiB `slice_backward` zero-fill and copy per micro-step, and it is the one line that can silently push the CE onto the eager fp32 path if the vocab ever changes.
- **Z6. Rebind instead of `copy_` in `_update` (lines 1205-1206).** `self.table.copy_(updated)` and `self.square_avg.copy_(second)` are two eager 128 MiB copies (about 3 to 6 ms every 2 steps). The compiled core never sees the table buffer (the gather at line 998 is eager), so `model.value_bigram_table = updated` (re-registering the buffer so `state_dict()` still finds it) and `self.square_avg = second` are exact and free. Keep `self.table` pointing at the model's buffer attribute.
- **Z7. Persistent device scalars for `weight` (line 1173), `ramp_backward_seed` (1645), `mtp_weights` (1652), `lr`/`correction` (1202-1203).** Use the same host-buffer + `dev.copy_(host)` pattern as `_device_scalar` (1217-1229), or precompute the two possible `weight` values (accum 1 and 2) once. Removes 5 synchronising allocations per step; the one at 1173 sits right after `loss.backward()` and stalls the next launch.
- **Z8. Fold the three tiny per-step collectives into one** (lines 1568, 1499, 1709): one int32 vector all_reduce (MAX) per step carrying ramp phase, table control and the loss/stop flags, read back with one `.tolist()` after the existing `synchronize`. Saves two host round trips per step.
- **Z9. Delete dead paths in the compiled function** (lines 736-738 GQA repeat, 751-752, 757-758, 841-842): no runtime cost today, but they keep dynamo guards and make the traced graph harder to read in the profile.
- **Z10. Wrap `_rope_norm_fwd/_bwd` with `torch_neuronx.wrap_nki` and launch with `[2]`** exactly as the CE and conv kernels are (see graph-break audit). Zero new math; potentially the largest single fix in this list if the bare call is graph-breaking or running on one core.
- **Z11. `fullgraph=True` on `compile_core`** (line 992) as an assertion that Z10 holds and stays held.
- Not zero-engineering but one line and near-identical math: **bf16 cached embedding tables** for `wte` and `value_embeds['7']` (refresh like `Linear._cached_weight`), which removes the two fp32-to-bf16 cast passes and halves the scatter bytes; the scatter then accumulates in bf16 (a numerics change to check).
